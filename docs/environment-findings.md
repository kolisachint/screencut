# screencut — environment findings (phase 0)

The deliverable of phase 0 in [`implementation-phases.md`](implementation-phases.md):
measured numbers in place of the four assumptions phase 4 onward is blocked on.

Raw results are committed under [`measurements/`](measurements/) and are regenerated by
the scripts in `tools/phase0/`. Every number below came from one of those files; nothing
here was typed from memory.

**Measured on** Apple M1, 8 GB, 8 cores, macOS 27.0 (arm64), 2026-08-30 — the base-model
fanless M1 Air of `architecture.md` §16, not a stand-in for it.

## 1. Read this before trusting any memory number

**Resident set size is the wrong metric on this machine.** MLX allocates through unified
memory, and those allocations do not appear in RSS. The same mlx-whisper `large-v3` run:

| Metric | Value |
|---|---|
| `maximum resident set size` | 1 327 MB |
| `mx.get_peak_memory()` | 3 512 MB |
| **`peak memory footprint`** (macOS `phys_footprint`) | **5 664 MB** |

RSS is off by 4.3×. Footprint is what macOS charges and therefore what decides whether an
8 GB machine swaps, so every memory figure below is footprint. `tools/measure.py` wraps
every child in `/usr/bin/time -l` for exactly this reason and reports both — the gap
between them is itself a finding.

This was caught late. The first serialization result was incoherent (the resident case
appeared to use *less* memory than the serial one) and only made sense once footprint was
measured. A benchmark reporting RSS alone would have chosen the ASR model wrongly and
looked reasonable doing it.

## 2. R1 — cursor events are extractable

Against a real Cap take (`~/Library/Application Support/so.cap.desktop/recordings/*.cap`).
`content/segments/segment-0/cursor.json` holds two arrays:

```json
moves:  {"time_ms": 1262.93, "x": 0.0805, "y": 0.5347, "cursor_id": "1", "active_modifiers": []}
clicks: {"time_ms": 839.62, "down": true, "cursor_num": 1, "cursor_id": "0", "active_modifiers": []}
```

**`x` and `y` are already normalized to 0..1** — the same space as `spec/types.py`'s
`Normalized`. The adapter needs no pixel conversion at all, which removes an entire class
of the rounding bugs `AGENTS.md` warns about. `FocusTrack` survives contact with reality.

Also present and unasked for: keyboard events (`keyboard.bin`), cursor bitmaps with
hotspots, and per-segment structure for multi-take work (decision #24).

### Three traps the adapter must handle

**Sampling is event-driven, not fixed-rate.** Median 37 Hz, mean 17 Hz, p95 gap 111 ms —
but the **maximum gap is 1 981 ms**. A cursor at rest emits nothing at all. This sharpens
`AGENTS.md`'s existing "dwell measured between adjacent samples" trap into something
worse: dwell is not merely mismeasured across adjacent samples, it is *invisible*, because
resting produces no samples to measure between. The adapter must resample to a fixed grid
before `plan_focus` sees it, and absence must be read as dwell rather than as no data.

**Clicks carry no position.** They have only a time and a `down` flag, so a click's
location has to be interpolated from the surrounding `moves`. The worst nearest-sample
distance in this take was **423 ms** — long enough for a moving cursor to be somewhere
else entirely. Click-cluster zoom targeting inherits that error and should interpolate
between bracketing samples, not snap to the nearest.

**Two clocks.** Cursor `time_ms` is on the recording clock; the video starts
`start_time = 0.194 s` later. Ignoring it offsets every zoom by ~0.2 s, which reads as a
planner bug rather than a clock bug. §4.5 permits one time base — seconds from source
start — so the adapter subtracts `start_time` once, at the boundary.

And a fourth, smaller: `recording-meta.json` claims `fps: 25` while the stream is
**59 fps** (2560×1440). Trust `ffprobe`, not the sidecar.

## 3. ASR — three backends, two sizes

44.4 s of speech, known reference script. Sustained is the median of repeats; WER is
against the reference. All figures footprint.

| Backend | Size | Burst | Sustained | Footprint | ×realtime | Word timings | WER |
|---|---|---|---|---|---|---|---|
| whisper.cpp | medium | 8.8 s | **8.8 s** | **2 132 MB** | **5.05×** | yes | 0.028 |
| mlx-whisper | medium | 12.1 s | 12.3 s | 3 616 MB | 3.60× | yes | **0.007** |
| faster-whisper | medium | 26.2 s | 27.3 s | 1 899 MB | 1.62× | yes | 0.007 |
| whisper.cpp | large-v3 | 22.9 s | **22.7 s** | 3 984 MB | 1.95× | yes | 0.007 |
| mlx-whisper | large-v3 | 42.4 s | 37.6 s | **5 401 MB** | 1.18× | yes | 0.007 |
| faster-whisper | large-v3 | 53.9 s | 57.0 s | 3 444 MB | 0.78× | yes | 0.007 |

**All three emit word-level timings**, so §6.2's `CaptionBlock` and phase 4's
`plan_captions` are unblocked whichever wins. That was the capability gate; the rest is
preference.

**whisper.cpp wins at both sizes** — fastest, and its footprint tracks its RSS so the
budget is predictable. mlx-whisper is the memory trap: 5 401 MB for `large-v3` is 66 % of
this machine, against an RSS reading of 2 467 MB that looks perfectly safe.

**CTranslate2/MPS, confirmed firsthand:** `device="mps"` raises `unsupported device mps`,
`get_cuda_device_count()` is 0, and `device="auto"` silently resolves to CPU. faster-whisper
is a CPU-only path here and its numbers show it.

**The phases doc's hypothesis holds.** "On 8GB the smaller model winning on wall-clock is a
live possibility rather than a consolation prize" — `medium` is 2.6× faster than `large-v3`
on whisper.cpp and saves 1.9 GB. It is not a consolation prize; it is the default.

The WER column mostly does not discriminate, because a clean `say` voice is the easy case
and five of six runs tie at 0.007. Only whisper.cpp/medium is meaningfully worse (0.028).
Treat this as a floor, not a ranking — real takes with room tone and hesitation are what
phase 4 will actually retune against.

**Recommendation for `constraints.yaml`:** `whisper.cpp`, size `large-v3` (1.95× realtime,
3 984 MB, WER 0.007). It leaves ~4 GB for the OS, and `medium` is the documented fallback
when memory is contended — 5× realtime for a WER cost that is real but small.

## 4. F5-TTS — not viable locally

| Path | Text | Result | Infer | Audio | ×realtime |
|---|---|---|---|---|---|
| MPS | single batch | ok | 46.2 s | 5.2 s | 0.11× |
| MPS + fallback env | single batch | ok | 47.2 s | 5.2 s | 0.11× |
| CPU | single batch | ok | 112.4 s | 5.2 s | 0.05× |
| MPS | 30 s (3 batches) | **SIGSEGV** | — | — | — |
| MPS + fallback env | 30 s (3 batches) | **SIGABRT** | — | — | — |
| CPU | 30 s (3 batches) | ok | 607.0 s | 31.8 s | 0.05× |

**MPS works and is 2.2× faster than CPU — until it batches.** F5-TTS splits long text into
chunks, and the chunked path aborts. Only CPU completes a 30-second synthesis, and it takes
**ten minutes** to do it. A three-minute narration would cost about an hour.

`PYTORCH_ENABLE_MPS_FALLBACK=1` is **not** needed; it changes nothing either way.

**Verdict: no.** Per the phases doc this blocks nothing — phase 8 begins by building
`RemoteRunner`, which is precisely the substitution the stage-contract seam exists to
absorb. Read this section before starting phase 8, not after.

### Two integration hazards worth carrying forward

**A successful synthesis can still exit nonzero.** F5-TTS pulls in `multiprocess`, whose
resource tracker respawns the interpreter with an empty `PYTHONHASHSEED` and dies on
Python 3.12 with `Fatal Python error: config_init_hash_seed`. It dies at *teardown*, after
good audio has been written, but it takes the exit code with it. §7.4 counts a nonzero exit
as stage failure, so a `tts` stage would have degraded on every successful run. Setting
`PYTHONHASHSEED=0` fixes the exit code.

This bit the benchmark before it could bite the pipeline: the first TTS pass recorded
F5-TTS as broken on all three paths. The harness was wrong, not the machine. `bench_tts.py`
now judges success by produced audio rather than by exit status.

**Two libraries, one FFmpeg.** `torchaudio` 2.13 loads audio through `torchcodec`, which
dlopens FFmpeg by soname and does not find Homebrew's without
`DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib`. Setting it then makes PyAV's *bundled*
FFmpeg collide with Homebrew's — duplicate Obj-C classes, and the warning text promises
"mysterious crashes", which is what the MPS segfaults were. Importing `mlx_whisper` and
`f5_tts` into one process breaks it a third way.

This is an argument *for* §5.1's subprocess stage contract: separate processes cannot
collide like this. Routing audio loading through `soundfile` avoids the whole knot.

## 5. Memory budget and serialization (§16)

Per-stage footprint, which is what `constraints.yaml` and `LocalRunner` should reason about:

| Stage | Footprint | Note |
|---|---|---|
| `render` (software / libx264) | 693 MB | RSS; footprint tracks it |
| `render` (videotoolbox) | 174 MB | |
| `transcribe` (whisper.cpp large-v3) | 3 984 MB | recommended |
| `transcribe` (whisper.cpp medium) | 2 132 MB | fallback |
| `transcribe` (mlx-whisper large-v3) | 5 401 MB | **66 % of RAM** |
| `tts` (F5-TTS, CPU) | ~2 500 MB | not viable on speed |
| model stages (agent CLI) | negligible | no local weights, so exempt from serialization |

The machine was already carrying **2.8–5.4 GB of swap in use** before any benchmark
started. That is the ambient condition on a working 8 GB laptop and it is why the ceiling
here is treated as ~5.5 GB rather than 8 GB.

**Serialization is required**, and the reason is arithmetic rather than subtle: the
recommended `transcribe` stage alone is 3 984 MB against a ~5 500 MB working ceiling, and
mlx-whisper `large-v3` is 5 401 MB by itself. Two concurrent local-inference stages do not
fit at any pairing that includes ASR. `LocalRunner`'s existing refusal to start a second
weight-holding stage is correct and now has a number behind it. Agent-CLI stages hold
nothing locally and remain exempt, which is what makes them the ones that parallelize.

**The direct experiment did not produce a clean number, and this verdict does not rest on
it.** `bench_serialize.py` was meant to run transcribe-then-synthesize in one process and
watch for swap. It kept being confounded rather than answered: first by RSS hiding MLX's
allocations (the resident case appeared to use 1.2 GB *less* than the serial one, which is
impossible), then by the FFmpeg library conflict of §4 — `mlx_whisper` and `f5_tts` in one
process break each other's audio loading, so the resident arrangement fails for a reason
that has nothing to do with memory. `measurements/serialization.json` records that
outcome, including the failures; it should be read as "inconclusive", not as evidence.

That is not a wasted result. The reason the resident case cannot be made to work is itself
an argument for §5.1's subprocess stage contract: two model stages sharing an address
space collide over native libraries before they ever collide over memory. The serialization
constraint is carried by the per-stage footprints above, which are measured and
unambiguous.

## 6. Encode — both paths present

60 s of 1080p30, three runs back to back.

| Path | Burst | Sustained | Peak | ×realtime |
|---|---|---|---|---|
| `h264_videotoolbox` | 9.30 s | **9.10 s** | 174 MB | 6.60× |
| `libx264` (bitexact, crf 20) | 17.98 s | **19.71 s** | 693 MB | 3.04× |

`h264_videotoolbox` is present and works. **Software costs 2.17× hardware**, which is the
price the golden set pays on every replay — affordable.

The burst/sustained split behaves exactly as a fanless chassis predicts, and this is the
clearest illustration of why the phases doc insists on the distinction: VideoToolbox is
fixed-function and *held* its speed (9.30 → 9.10 s), while `libx264` is eight cores of
general compute and **got slower under sustained load** (17.98 → 19.71 s, 10 % worse). A
single-run benchmark would have reported the software path 10 % cheaper than it is.

## 7. R5 — the agent CLI round-trips a schema

The §7.3 invocation, run for real: `hoocode -p --mode json --no-tools --no-session`, fixed
cwd, full JSON Schema in the prompt. Twelve trials against a throwaway fragment schema with
enums, nested arrays and bounded strings.

| Model | Trials | Schema-valid | Fenced | Burst | Sustained | Min | Max |
|---|---|---|---|---|---|---|---|
| claude-sonnet-5 | 6 | **6/6** | 5/6 | 12.0 s | 16.1 s | 5.7 s | 26.1 s |
| claude-haiku-4-5 | 6 | **6/6** | 6/6 | 47.8 s | 35.6 s | 19.5 s | 65.8 s |

**12/12 schema-valid.** Better than §7.2's expected "mostly", though twelve trials is an
environment spike and not the real rate — phase 9's replay measures that.

**11/12 arrived wrapped in a ```json fence.** The adapter must strip fences before parsing.
This is not a schema violation and must not be counted as one, or R5 looks worse than it is
and phase 5 chases the wrong mitigation. `tools/phase0/bench_agent.py::extract_fragment`
records the extraction that worked: last assistant `message_end` in the event stream, strip
a fence if present, else take the outermost braces.

**Latency is the real finding, and it is worse than the schema risk.** The floor is 5.7 s;
typical is 12–36 s; worst observed is **65.8 s**, an 11× spread on identical input. Every
model stage pays this, so §5.2's cache is not an optimization for the review loop — it is
what makes the loop exist. Phase 5 should assume tens of seconds per stage and set timeouts
against the maximum, not the median.

Haiku was consistently *slower* than Sonnet, which inverts the usual expectation. On twelve
trials that is more likely queueing variance than a property of the models; do not read a
model-selection conclusion into it.

## 8. Toolchain — what had to be fixed to run anything

None of this was in the plan, and all of it blocked the existing test suite.

**Homebrew's `ffmpeg` has no libass.** The formula does not depend on it — `brew deps
ffmpeg` lists no `libass`, and there is no `ass` or `subtitles` filter in the build. Caption
burn-in is impossible with it and `tests/test_render.py` fails with FFmpeg exit 8. The fix
is the keg-only **`ffmpeg-full`** (9.0.1: libass, `zoompan`, `sendcmd`, `libx264`,
`h264_videotoolbox`, 2 966 fonts). It is not symlinked, so
`/opt/homebrew/opt/ffmpeg-full/bin` must lead on `PATH`.

`AGENTS.md` already said "needs ffmpeg with libass". What it could not say is that the
obvious way to install ffmpeg now produces one without.

**FFmpeg 9 removed `-filter_complex_script`, which the render stage uses.** Installing
`ffmpeg-full` fixes libass and immediately exposes this: `runner/stages.py` builds its
command with `-filter_complex_script graph.txt`, the option no longer exists, and FFmpeg
exits 8 with `Error splitting the argument list: Option not found`. Twenty tests fail on it.

The replacement is the generic read-option-from-file syntax, verified end to end on this
machine — `-/filter_complex graph.txt` renders the fixture and exits 0. It is deliberately
**not** applied here, because phase 0 excludes pipeline code and the change wants a
version guard rather than a substitution: `-/filter_complex` does not exist before FFmpeg 7,
so a straight swap trades one incompatibility for another. This is the first thing phase 4
should do, and it is a ten-line change with a real decision inside it.

Until then the suite passes only against an FFmpeg older than 9, which no longer ships
libass — so on a clean macOS box today there is no single FFmpeg that satisfies both. That
is the finding, and it is why it is written down rather than patched around.

**`python3` on this machine is 3.9.6**; the project requires ≥ 3.11 and `make` calls
`python3` directly. Work in a 3.12 virtualenv.

**cairosvg cannot find libcairo.** `cairocffi` looks for `libcairo-2.dll` (sic) and misses
Homebrew's arm64 install; four test modules fail to import. Needs
`DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib`. The same variable that fixes this is the one
that breaks F5-TTS's MPS path — they want different FFmpeg libraries and cannot both be
satisfied by one global setting, which is another reason stages are subprocesses.
